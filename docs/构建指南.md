# 构建指南

从零构建出 `maa-fnos.fpk`。整个过程分两段：**先做 Docker 镜像**，**再打 fpk 包**。

> 💡 镜像构建比较吃资源（1.15GB 镜像、解压 400MB+ 的官方包），
> 建议丢到另一台有 Docker 的机器上做，再把产物拷回 NAS。**不要**在你日常用的飞牛上跑构建。

---

## 0. 前置条件

| 依赖 | 说明 |
|---|---|
| Docker | 构建机需安装，版本不限（实测 Docker 29.x 可用） |
| `fnpack` | 飞牛官方打包工具，只在打 fpk 那一步需要 |
| `python3` + Pillow | 仅当你要重新生成图标 |
| 磁盘 | 至少 6GB 空闲 |

`fnpack` 下载（1.2.3，linux-amd64）：

```bash
curl -fL -o fnpack https://static2.fnnas.com/fnpack/fnpack-1.2.3-linux-amd64
chmod +x fnpack && sudo mv fnpack /usr/local/bin/
fnpack build --help
```

> `fnpack` 1.2.3 没有 `--version` 子命令，用它来确认安装情况会直接报错；改用
> `fnpack build --help` 即可看到可用参数。

## 1. 准备两个上游产物

### 1.1 MAA 官方 Linux 版

从 [MAA Releases](https://github.com/MaaAssistantArknights/MaaAssistantArknights/releases) 下载 **Linux x86_64** 包，
重命名为 `maa-linux.tar.gz`。

> ⚠️ 官方包要求 **glibc ≥ 2.38**，所以下面的基础镜像必须是 Ubuntu 24.04（glibc 2.39）或更新。
> 本项目验证过的核心版本：**MAA v6.17.5**。

```bash
# 校验完整性
gzip -t maa-linux.tar.gz && echo "tarball OK"

# 看一眼版本
tar -tzf maa-linux.tar.gz | head
```

### 1.2 MAA-WEB-CONTROL 源码

**单仓布局：Web 前端就在本仓库的 `MAA-WEB-CONTROL-master/` 目录下，不发布、不回馈上游。**

本应用通过飞牛统一网关的 unix socket 对外提供服务，因此 Web 源码目录里需要一个启动器
`serve_socket.py`（自建 socket → 清掉旧路径 → 交给 uvicorn 用 `--uds` 创建）。
上游 `KlN-4096/MAA-WEB-CONTROL` 没有这段改造，用它构建出来的镜像不会去 listen 网关给的
socket，装上去应用中心会一直显示异常 —— 所以仓库里这份源码**必须**带上这个文件。

```bash
# 单仓：直接看仓库根下的 MAA-WEB-CONTROL-master/（Dockerfile COPY 的就是这个名字）
ls MAA-WEB-CONTROL-master/app              # 应有 main.py / api.py ...
ls MAA-WEB-CONTROL-master/serve_socket.py  # 网关启动器，缺了构建会失败

# 需要改用仓库外的副本时才传 MAA_WEB_SOURCE（目录本名不限，脚本会按目标名落进上下文）
MAA_BUILD_WORK=/data/maa-work MAA_WEB_SOURCE=/path/to/MAA-WEB-CONTROL-master \
  bash deploy/build.sh
```

> `deploy/build.sh` 会检查 `serve_socket.py`，缺文件直接报错退出，**没有跳过开关**：
> 缺了网关入口就打不开，这种镜像没有存在意义。

## 2. 构建 Docker 镜像

`deploy/Dockerfile` 是三段式：装运行期依赖 → 铺 MAA 官方包 → 铺 Web 前端。
**注意 `COPY redroid-proxy/docker /usr/local/bin/docker` 这一层**，它是 redroid 状态查询的关键。
构建上下文里必须有核心包、Web 源码、`redroid-proxy/` 和 `deploy/`（Dockerfile 在里面）：

```bash
# 构建上下文：核心 tar + Web 源码 + redroid-proxy/ + deploy/
mkdir -p ~/maa-build && cd ~/maa-build
cp /path/to/maa-linux.tar.gz .
cp -r /path/to/MAA-WEB-CONTROL-master .
cp -r /path/to/MAA-FnOS/redroid-proxy .
cp -r /path/to/MAA-FnOS/deploy .

# 用 -f 指到上下文里的 deploy/Dockerfile
#   注意：Dockerfile 里 COPY 的是 redroid-proxy/docker，这一层必须在上下文根
docker build -f deploy/Dockerfile -t maa-fnos:local \
  --build-arg MAA_TARBALL=maa-linux.tar.gz .
```

或者直接用仓库里的脚本（**推荐**，只有「copy 源码 → docker build」两步，不做任何 patch）：

```bash
# MAA_BUILD_WORK 必填：独立的绝对构建目录（放官方包与构建上下文）
MAA_BUILD_WORK=/data/maa-work bash deploy/build.sh

# 可选：
#   MAA_WEB_SOURCE=/path/to/MAA-WEB-CONTROL-master   默认取仓库内 MAA-WEB-CONTROL-master/
#   MAA_IMAGE_TAG=maa-fnos:local                      输出镜像 tag
```

脚本做的事（固定顺序，无第二次覆盖/补丁）：

```text
1. 校验 $MAA_BUILD_WORK/maa-linux.tar.gz 可解压
   校验 $WEB_SRC 存在；必须存在 serve_socket.py（否则报错退出，无跳过开关）
2. CTX=$(mktemp -d)          # 每次新目录，不复用旧上下文
   cp maa-linux.tar.gz  $CTX/
   cp -r $WEB_SRC       $CTX/MAA-WEB-CONTROL-master   # 工作区源码原样拷入
   cp Dockerfile        $CTX/
   cp -r redroid-proxy  $CTX/
3. docker build -t $IMAGE_TAG --build-arg MAA_TARBALL=maa-linux.tar.gz $CTX
```

> 因为上下文每次都是全新的 `mktemp -d`、源码只 `cp` 一次、之后没有任何改写步骤，
> 所以**不存在「补丁被打两次」或「旧改动残留」的可能**：镜像里的 Web 文件就是
> 你工作区里那棵树的字节级副本。

构建成功后确认：

```bash
docker images maa-fnos:local
# REPOSITORY   TAG     IMAGE ID       SIZE
# maa-fnos      local   <本次构建的 ID>  <本次构建的大小>
# 具体 IMAGE ID / SIZE 以本次构建的实际输出为准（每次重建镜像 ID 都会变）。
```

### 2.1 冒烟测试（推荐，省得打完整包才发现问题）

# 起一个临时容器
docker run -d --name maa-smoke --restart no -p 18000:8000 \

## 3. 导出并压缩镜像

fpk 要内置离线镜像，所以得把镜像导成 tar 再压：

```bash
docker save maa-fnos:local | gzip -9 > maa-image.tar.gz

ls -lh maa-image.tar.gz
# 具体大小以本次输出的实际值为准（未压缩约等于镜像体积，gzip 大致能压掉一半）
```

> 关于压缩级别：`-9` 最省体积但慢；`-6` 是速度/体积平衡点，差别约 1~2%。
> **每次重建镜像后 docker image ID 都会变**，这正是 1.0.2 引入「镜像指纹比对」的原因。

## 4. 组装并打包 fpk

```bash
cd fnos-app
cp ../maa-image.tar.gz app/
ls -la app/          # 应看到 maa-image.tar.gz

fnpack build
ls -la *.fpk         # 约 613MB
```

`fnpack` 会强制校验这几样，缺一样都会报错：

- `manifest` 里的 `desktop_uidir`（本项目为 `ui`）与 `app/ui/` 目录必须同时存在
- 包根必须有 `ICON.PNG`（64x64）与 `ICON_256.PNG`（256x256）
- `manifest` 必填字段：`appname` / `version` / `display_name` / `platform` / `source` /
  `maintainer` / `distributor` / `desktop_uidir` / `desktop_applaunchname` / `ctl_stop` / `os_min_version`

仓库里的 `assemble.sh` 是给「从官方骨架复制 + 覆盖定制文件」的场景用的，按需修改。

## 5. 安装到飞牛

```bash
# 传到 NAS（大文件走内网 rsync 更快）
rsync -avP --partial --inplace maa-fnos.fpk <user>@<NAS_IP>:/home/<user>/

# NAS 上安装
sudo appcenter-cli install-fpk --volume 1 /home/<user>/maa-fnos.fpk

# 启动并发起状态检查
sudo appcenter-cli start maa-fnos
sudo appcenter-cli status maa-fnos      # 返回 0 = running
```

## 6. 发布前验收清单

先记清楚安装后两套路径各放什么，不然检查命令会全部落空：

| 路径 | 内容 |
|---|---|
| `/var/apps/maa-fnos/` | `manifest`、`cmd/`、`config/`、`wizard/`、`ICON*.PNG` |
| `/var/apps/maa-fnos/target` | 软链 → `/vol1/@appcenter/maa-fnos`（即 `TRIM_APPDEST`，`app/` 的内容） |
| `/vol1/@appdata/maa-fnos/` | 运行期数据（即 `TRIM_PKGVAR`），日志、`maa-data/`、网关 socket 都在这里 |

```bash
grep ^version /var/apps/maa-fnos/manifest                             # 版本号已递增
sudo appcenter-cli status maa-fnos                                    # running
sudo docker ps --filter name=maa-fnos                                 # Up（不再映射宿主机端口）
sudo docker inspect maa-fnos --format '{{.HostConfig.RestartPolicy.Name}}'

# 网关 socket：属主是 package 用户（maa-fnos）、权限 srw-------。
ls -l /vol1/@appdata/maa-fnos/gateway/app.sock
# 探活要用 package 用户身份跑 —— cmd/main 就是这么探的。socket 是 0600，
# 换别的身份可能连不上，那样会把一个健康的应用误判成失败。
sudo -u maa-fnos curl -s --unix-socket /var/apps/maa-fnos/target/app.sock http://localhost/api/status
# 期望：{"state":"Idle", ...} 之类的 JSON

ls /vol1/@appcenter/maa-fnos/ui/images/ | wc -l                       # 12（图标齐全）
cat /vol1/@appcenter/maa-fnos/maa-image.id                            # 指纹 == docker image inspect --format '{{.Id}}'
                                                                      # 该文件由 cmd/main 在 docker load 之后写入
sudo docker images -f dangling=true                                   # 无遗留悬空镜像
ps -eo pid,etime,cmd | grep redroid_status_proxy | grep -v grep       # 只有应用起的那一个
grep -n 'CONTAINER=' /var/apps/maa-fnos/cmd/main                      # 容器名符合预期
```

> 想确认某个改动真的进了安装后的应用，直接看 `/var/apps/maa-fnos/`；
> 想看用户数据有没有被动过，看 `/vol1/@appdata/maa-fnos/`。

## 常见构建问题

| 现象 | 原因 / 处理 |
|---|---|
| `maa: /lib/x86_64-linux-gnu/libc.so.6: version 'GLIBC_2.38' not found` | 基础镜像太老，必须用 `ubuntu:24.04` |
| `fnpack build` 报缺 `ICON.PNG` | 包根必须有大写 `ICON.PNG` 和 `ICON_256.PNG` |
| `fnpack build` 报 `desktop_uidir` 目录不存在 | `manifest` 声明了 `desktop_uidir = ui` 就必须有 `app/ui/` |
| 装完后打开是空白页 | 容器没起来。看 `/vol1/@appdata/maa-fnos/info.log` |
| 升级后跑的还是老版本 | 镜像没重新导入，看 CHANGELOG 里 1.0.2 的说明 |
